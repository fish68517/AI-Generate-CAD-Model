# 《CAD-Coder》图4、图5及类似案例复现方案

> 论文：Anna C. Doris 等，*CAD-Coder: An Open-Source Vision-Language Model for Computer-Aided Design Code Generation*，arXiv:2505.14646v1，2025-05-20。  
> 本地论文文件：`doc/2505.14646v1.pdf`，15页，SHA256：`415D764D78DBFDA4DCBD773373BB68F9DB4EB724F24258B71C5655CE6A29CEF2`。  
> 分析日期：2026-08-25。  
> 当前工程：`E:\code\论文复现`，已有主线是 CADmium 的“文本 → 最小 CAD JSON → STL”轻量复现。

## 1. 先给结论

图4、图5不能作为现有 CADmium 工程里的“再增加几个文本样例”直接完成。论文研究的是 **CAD-Coder**，它的主链路是：

```text
输入图片 + 固定文本指令
        ↓
LLaVA 1.5 型视觉语言模型
CLIP-ViT-L-336px + Vicuna/Qwen2.5-Coder
        ↓
可执行 CadQuery Python 代码
        ↓
CadQuery / OpenCascade
        ↓
STEP、STL、3D实体、VSR、IOUbest
```

而当前 CADmium 工程是：

```text
自然语言 annotation
        ↓
Qwen2.5-Coder-1.5B + CADmium LoRA
        ↓
最小 CAD JSON
        ↓
本地 JSON 几何重建
        ↓
STL、Chamfer Distance、watertight 等指标
```

二者的输入模态、模型架构、输出表示、几何内核和评价指标均不同。因此建议保留现有 CADmium 主线，新增相互隔离的 `cadcoder_repro` 子工程，不修改现有 CADmium 数据格式和推理脚本。

推荐目标分成三档：

| 复现等级 | 含义 | 当前可行性 | 建议 |
|---|---|---:|---|
| A. 工程链路复现 | 图片 → 代码 → STEP/STL → 指标 → 图表 | 高，但模型推理需云 GPU | 首先完成 |
| B. 论文对齐的类似案例 | 自建5个真实照片案例和圆角编辑案例，方法及版式对齐图4/图5 | 中高 | 本阶段主目标 |
| C. 论文原图精确复现 | 使用原始5张照片、全部模型变体和同一权重得到相同结果 | 低 | 暂不承诺 |

不能直接承诺 C 的原因是：截至本次核验，官方仓库公开了100条测试渲染图和对应 STEP，但未发现图4的原始真实照片；Hugging Face 仅公开了 13B BF16 的 `CADCODER/CAD-Coder`，未发现图5中的 Qwen2.5-14B 与 LowLR 两个变体权重。图5如要完全一致，需要自行重训变体。

## 2. 图4、图5到底验证什么

### 2.1 图4：从渲染域迁移到真实照片域

论文图4包含5列对象和4行结果：

1. 真实照片：将 GenCAD-Code 测试集对象3D打印后，在木桌上以近似等轴测角度拍摄；
2. 真实照片输入时，CAD-Coder 生成的实体；
3. 原始 CAD 渲染图输入时，CAD-Coder 生成的实体；
4. Ground Truth 实体。

图4不是普通“看图生成模型”展示，它控制了同一个目标对象的两种输入域：

```text
真实照片 ──→ 同一模型 ──→ 预测实体 ──→ IOUbest(real)
渲染图片 ──→ 同一模型 ──→ 预测实体 ──→ IOUbest(render)
                                       ↓
                            比较真实域带来的性能下降
```

论文的5组 `IOUbest` 如下：

| 对象 | 真实照片输入 | 渲染图输入 | 主要现象 |
|---:|---:|---:|---|
| 1 | 0.989 | 0.989 | 简单台阶结构在两种输入域均表现好 |
| 2 | 0.401 | 0.719 | 操作类型大致正确，但真实照片下长宽比例估计错误 |
| 3 | 0.586 | 0.763 | 多次拉伸的复杂结构在真实照片下缺失或错判特征 |
| 4 | 0.303 | 0.914 | 薄板比例/厚度在真实照片下估计明显偏差 |
| 5 | 0.400 | 0.988 | 长条实体的比例在真实照片下偏差明显 |

论文据此只说明模型“显示出真实图像泛化迹象”，而不是已经证明其真实场景鲁棒性。样本量只有5，真实照片视角、颜色、纹理和背景也与训练时的灰色等轴测渲染图不同。

### 2.2 图5：未见过的 CAD 操作与灾难性遗忘

图5是两轮交互：

```text
第一轮：图片 + 固定指令 → 生成基础 CadQuery 实体代码
第二轮：要求在所有边上添加圆角，并提示 .edges().fillet(...) 语法
```

比较三个变体：

| 变体 | 预训练语言模型 | Stage 2 学习率 | 图5圆角结果 | 论文100样本 VSR | 论文 IOUbest |
|---|---|---:|---|---:|---:|
| CAD-Coder | Vicuna-13B-v1.5 | `2e-5` | 失败，输出扩展代码且语法错误 | 100% | 0.675 |
| CAD-Coder-Qwen2.5-14B | Qwen2.5-Coder-14B-Instruct | `2e-5` | 失败，错误使用 `.edges()` | 95% | 0.641 |
| CAD-Coder-Qwen2.5-14B-LowLR | Qwen2.5-Coder-14B-Instruct | `1e-5` | 在强提示下成功 | 94% | 0.592 |

图5的意义不是证明 LowLR 全面更好，而是说明：较低学习率可能更好地保留预训练模型已有的 CadQuery 知识，但会牺牲训练分布内的整体几何性能。论文还明确指出，LowLR 对抽象的“给所有边加圆角”提示并不稳定，成功依赖提示中明确写出 `.fillet()` 用法。

## 3. 论文方法与复现所需核心事实

### 3.1 数据

GenCAD-Code 将 GenCAD 的 CAD 命令转换为 CadQuery Python：

| 项目 | 论文值/当前公开值 |
|---|---|
| 总规模 | 163,671 个 CadQuery 脚本，每个配5张渲染图 |
| 训练集 | 147,289 |
| 测试集 | 7,355 |
| 验证集 | 论文写 9,027；当前 HF 数据卡显示 8,204，必须在复现实验中记录版本差异 |
| 平均代码长度 | 约611 token |
| 代码长度分布 | 99.9% 小于3000 token |
| Stage 2 过滤 | 总输入超过4096 token的极少量样本被过滤 |
| 输入文本 | 固定指令，不是自由文本描述 |
| 输出 | CadQuery Python，最后实体赋给变量 `solid` |

固定指令为：

```text
Generate the CadQuery code needed to create the CAD for the provided image.
Just the code, no other words.
```

### 3.2 模型

原始 CAD-Coder 使用 LLaVA 1.5 型架构：

- 视觉编码器：`openai/clip-vit-large-patch14-336`；
- 语言模型：`lmsys/vicuna-13b-v1.5`；
- 图像到语言映射：两层 `mlp2x_gelu` projector；
- 最大上下文：4096；
- Stage 1：冻结视觉编码器和 LLM，只训练 projector；
- Stage 2：冻结视觉编码器，训练 projector 和全部 LLM 参数；
- 论文主结果使用全量端到端微调，不是当前 CADmium 所使用的 LoRA/QLoRA。

### 3.3 论文训练资源

| 阶段/变体 | 论文资源 | 时间 | 关键参数 |
|---|---|---:|---|
| Stage 1 对齐 | 4 × H100 | 4.5小时 | 1 epoch，LR=`1e-3`，有效 batch=256 |
| Stage 2 CAD-Coder | 4 × H100 | 5.7小时 | 1 epoch，LR=`2e-5`，有效 batch=128 |
| Qwen2.5-14B Stage 2 | 8 × H100 | 3.31小时 | LR=`2e-5` |
| Qwen2.5-14B-LowLR Stage 2 | 8 × H100 | 3.31小时 | LR=`1e-5` |

这些时间只代表作者环境中的训练耗时，不包含下载、预处理、失败重跑、评估、快照上传和云服务器排队时间。

### 3.4 评价指标

1. **VSR（Valid Syntax Rate）**：生成脚本作为 Python 文件运行时无语法/运行错误的比例；
2. **IOUbest**：先按质心和惯性矩进行平移、尺度归一化，再枚举主轴方向对齐，取实体交并比最大值；
3. 论文的 `IOUbest` 只在成功执行的脚本上统计，不能与“将失败样本记0”的均值混用；
4. 论文100样本主实验使用 `temperature=0`、`max_new_tokens=3450`。

## 4. 与当前项目相比，难度增加在哪里

### 4.1 综合对比

| 维度 | 当前 CADmium 轻量复现 | 图4类似复现 | 图5类似复现 | 难度变化 |
|---|---|---|---|---|
| 输入 | 英文自然语言 | 336×336图片 + 固定文本 | 图片首轮 + 代码编辑次轮 | 从单模态变为多模态/多轮 |
| 模型 | 1.5B Qwen + LoRA | 13B LLaVA 型 VLM | 13B及14B多个变体 | 参数量约增一数量级 |
| 输出 | 受限 CAD JSON | 任意 CadQuery Python | 修改后的 CadQuery Python | 表达能力提高，安全风险也提高 |
| CAD操作 | 线、圆、圆弧、拉伸、有限布尔 | CadQuery/OpenCascade 全操作 | 需要圆角等当前 JSON 不可表示操作 | 必须更换输出表示和执行器 |
| 几何后端 | Trimesh/Shapely 轻量重建 | CadQuery/OCP B-Rep | CadQuery 圆角与边选择 | 依赖更重、拓扑更敏感 |
| 指标 | CD、体积、包围盒、watertight | VSR + IOUbest + 域差异 | 执行成功 + 圆角真实性 + 变体比较 | 指标需重新实现 |
| 数据 | 20条文本-JSON抽样 | 图像、代码、STEP、真实照片四类配对 | 两轮 prompt、基础代码、圆角代码 | 数据治理更复杂 |
| 推理资源 | 本机可CPU有限推理 | 官方 BF16 建议40/48GB以上显存 | 多变体推理且部分需重训 | 本机4GB无法运行 |
| 训练资源 | 后续24GB QLoRA烟雾测试 | 使用发布权重时无需训练 | 精确复现需8×H100级训练 | 图5精确复现显著更难 |
| 工程安全 | JSON解析后重建 | 模型输出可执行 Python | 继续执行模型修改后的 Python | 必须加入代码沙箱 |
| 可复现性 | 本地数据已固定 | 原始真实照片未公开 | 两个Qwen变体权重未公开 | 精确复现存在材料缺口 |

### 4.2 当前本机的实际边界

2026-08-25 本机检查结果：

- GPU：GTX 1050 Ti，4GB 显存，Compute Capability 6.1；
- CPU：i7-8750H，6核12线程；
- 内存：约32GB；
- E盘剩余：约59GiB；
- 当前 `.venv`：Python 3.10.6、CPU 版 PyTorch 2.6.0；
- 当前环境没有 `cadquery`，也没有可用 CUDA PyTorch；
- 官方模型：13B、BF16，Hugging Face 权重文件合计约24.87GB，权重本身已经超过4GB显存。

因此，本机适合：

- 论文、数据卡和代码静态分析；
- 下载小型100样本清单、渲染图和 STEP；
- 编写清单、图像预处理、日志、指标和排版脚本；
- 在单独 CadQuery 环境中执行少量代码、导出 STEP/STL、计算5个案例的 CPU 几何指标；
- 查看云端返回的代码和结果、制作图4/图5式例图。

本机不适合：

- 官方 13B BF16 VLM 推理；
- 13B/14B 全参数训练；
- 在4GB GPU上完成有论文可比性的量化推理；
- 复现4×H100或8×H100训练配置。

## 6. 推荐的总体实施路线

### 阶段0：固定证据与版本

1. 将官方仓库固定到当前核验 commit：`7f40b4827b029731ef97313a116d62519e313960`；
2. 保存论文 SHA256、模型 revision、数据集 revision、环境锁文件；
3. 保存官方100测试样本 JSONL、100张渲染图和100个 Ground Truth STEP；
4. 记录论文与当前 HF 数据卡的 validation 数量差异，不自行掩盖；
5. 对所有输入图片、STEP、模型响应和最终图表写 SHA256 manifest。

验收：任意案例可以通过 `case_id` 找回图片、prompt、响应、代码、STEP、STL、指标和渲染图。

### 阶段1：先完成不依赖模型的 CadQuery 闭环

在独立 `cad_iou` 环境中完成：

```text
官方 Ground Truth CadQuery/STEP
        ↓
CadQuery执行或STEP导入
        ↓
STEP + STL
        ↓
统一视角渲染
        ↓
IOUbest(self, self) ≈ 1.0
```

本阶段解决“模型之外”的问题：CadQuery版本、OCP布尔运算、STEP导出、图像渲染、主轴对齐和 IOU。必须先通过这一阶段，再租 GPU。

验收：

- 5个候选案例全部能导入/执行并生成 STEP、STL；
- `IOUbest(GT, GT)` 在数值误差范围内为1；
- 平移、缩放、轴翻转后的同一实体仍得到接近1的 `IOUbest`；
- 不同实体的 `IOUbest` 明显下降；
- 图表脚本能在没有模型输出时以“pending”占位，而不伪造结果。

### 阶段2：云端官方模型单样本烟雾测试

只选择一个最简单的长方体或薄板样本：

1. 加载 `CADCODER/CAD-Coder`；
2. 使用官方固定 prompt；
3. `temperature=0`，`max_new_tokens=3450`；
4. 保存原始模型输出，不先清洗覆盖；
5. 提取 Markdown code fence 内的 Python；
6. 在隔离的 CadQuery 执行环境中运行；
7. 成功后才扩展到5条和100条。

验收：模型、视觉塔和 tokenizer 正确加载；输出可追踪；至少1条产生 `solid` 并成功导出 STEP/STL；记录峰值显存和生成速度。

### 阶段3：图4类似案例复现

采用“同对象、双输入域”的严格成对设计，每个对象必须具备：

```json
{
  "case_id": "f4_01",
  "deepcad_id": "官方ID",
  "rendered_image": "等轴测渲染图",
  "real_photo": "真实拍摄图",
  "ground_truth_step": "目标STEP",
  "ground_truth_cadquery": "目标代码或来源",
  "prompt": "官方固定指令",
  "capture": {
    "camera": "设备型号",
    "view": "近似等轴测",
    "background": "背景说明",
    "crop_policy": "裁剪规则"
  }
}
```

#### 3.1 案例选择

建议5类由简单到复杂：

1. 单次拉伸台阶块；
2. 细长立柱；
3. 两次或多次拉伸的凹槽/盒形件；
4. 薄板；
5. 长条梁。

选择时优先从官方100样本中挑选，同时控制操作复杂度，避免5个案例全是简单长方体。每个对象保留操作数、代码 token、包围盒比例等元数据。

#### 3.2 真实照片获取

优先级如下：

1. 3D打印所选 Ground Truth，使用手机在近似等轴测角度拍摄；
2. 如暂时没有打印机，使用尺寸已知、可手工写出 Ground Truth CadQuery 的简单实体；
3. 不建议把另一张渲染图称作“真实照片”；若只能做材质渲染，必须标记为 `synthetic_real_like`。

拍摄要求：

- 原图保留，不覆盖；
- 统一裁剪为方形并缩放到336×336供模型使用；
- 同时保存相机原图、裁剪框、缩放方式；
- 视角尽量接近等轴测，但保留真实世界的纹理、阴影和透视；
- 物体尽量占画面相似比例；
- 不通过反复挑图只保留模型表现最好的结果。

#### 3.3 推理与输出

每个案例做两次推理：

```text
f4_01_real     = real_photo + official_prompt
f4_01_rendered = rendered_image + official_prompt
```

每次保存：输入图片 SHA256、完整 prompt、模型 revision、生成参数、原始回答、抽取代码、stderr、执行时间、STEP/STL、VSR状态、IOUbest、渲染图。

#### 3.4 图4式排版

最终输出 `reports/cadcoder/figure4_like/figure4_like.png`：

```text
第1行：Real Photo
第2行：Real-Image-Conditioned Prediction + IOUbest
第3行：Rendered-CAD-Image-Conditioned Prediction + IOUbest
第4行：Ground Truth
```

同时输出 CSV/JSON 表格，不能只保留拼图。

### 阶段4：图5类似案例复现

图5应分为三个层次，避免一开始就投入8×H100重训。

#### 4.1 执行器 Oracle 测试

先不用模型，对一个长方体执行：

```python
solid = solid.edges().fillet(0.01)
```

确认 CadQuery 版本支持、圆角半径合法、STEP/STL可导出、渲染图能显示曲面。这只证明工程执行链路正确，不计为模型复现结果。

#### 4.2 发布版 CAD-Coder 两轮测试

第一轮用图片生成基础实体；第二轮使用论文强提示：

```text
Add fillets to all the edges. Recall that you can do this using
solid.edges().fillet(fillet_radius), where I would like fillet_radius to be 0.01.
```

需要完整保留两轮对话上下文。评价不能只搜索字符串 `.fillet(`，而要同时检查：

- 第二轮代码语法和运行是否成功；
- 是否生成 `solid`；
- 是否使用了合理边选择和半径；
- STEP 中是否出现真实圆角曲面；
- 与基础实体相比体积/表面积/边类型是否发生合理变化；
- 统一视角渲染下是否能看到圆角。

#### 4.3 可负担的“类似变体”比较

由于图5的两个 Qwen VLM 权重未公开，先做明确标注的方法对照：

| 对照 | 输入 | 作用 | 是否等价论文变体 |
|---|---|---|---|
| Released CAD-Coder 13B | 图片 + 两轮对话 | 复现论文主模型失败/成功边界 | 是主模型 |
| Qwen2.5-Coder-14B 文本代码编辑 | 第一轮代码 + 圆角指令 | 验证预训练 CadQuery 知识 | 否，缺少视觉链路 |
| 小样本 LowLR LoRA/QLoRA | 第一轮代码 + 编辑对 | 验证低学习率/知识保留思路 | 否，是工程化近似 |
| Oracle CadQuery | 人工正确修改 | 验证执行与几何指标上限 | 否，是工具基线 |

这能形成“类似图5”的可解释实验，但不能把它写成论文三个原模型的精确复现。

#### 4.4 精确图5的后续重训路线

若后续必须精确复现：

1. 根据官方 LLaVA fork 将语言模型替换为 Qwen2.5-Coder-14B-Instruct；
2. 解决 tokenizer、对话模板、embedding、位置编码和 LLaVA projector 适配；
3. 使用同一个 Stage 1 checkpoint 或按论文架构重做视觉对齐；
4. Stage 2 分别以 `2e-5`、`1e-5` 全参数训练；
5. 同时运行100样本 VSR/IOUbest，不能只挑圆角成功案例；
6. 测试强提示与抽象提示，报告提示依赖性；
7. 保存训练曲线、checkpoint、峰值显存、数据 revision 和失败样本。

该路线需要8×H100级云资源，工程适配和训练失败风险均高，建议在图4及发布版图5测试完成后再决定是否投入。

## 7. 云服务器方案

### 7.1 官方13B推理

| 配置 | 能做什么 | 结论 |
|---|---|---|
| 本机 GTX 1050 Ti 4GB | 数据准备、CPU几何和图表 | 不能加载模型 |
| 单卡24GB + 4bit | 1条/5条工程推理、流程验证 | 可尝试，但不是论文 BF16 条件 |
| 单卡40GB | BF16 单样本推理通常更可行 | 可作为最低正式候选，需实测峰值 |
| 单卡48GB | BF16单样本和小批量更安全 | 推荐图4/图5推理 |
| 单卡80GB | 最宽裕，便于长输出和调试 | 推荐资源充足时使用 |

官方 BF16 权重约24.87GB，运行还需要视觉塔、激活、KV cache、CUDA kernel 和临时张量。因此“显存刚好大于权重文件”不等于可以稳定推理。24GB仅建议4bit工程近似；论文对齐优先选择 L40S/A6000/A40 48GB或A100/H100 80GB。

云端建议：Ubuntu 22.04、Python 3.10、CUDA与 PyTorch 2.1.2匹配、磁盘至少100GB；如果同时保存数据、多个模型和输出，准备150GB以上。训练阶段建议300GB以上并使用可恢复数据盘。

### 7.2 训练

- 论文主模型全量复现：按4×H100规划；
- 图5两个 Qwen 变体：按8×H100规划；
- 单卡 LoRA/QLoRA 只能算资源优化近似，不是论文全参数训练；
- 租用前先用 `--dry-run`、1条数据、1个前向步骤验证版本和显存；
- 每100/500步保存可恢复 checkpoint，使用持久化云盘；
- 费用按“实例单价 × 实际小时 + 磁盘 + 下行流量”计算，不能直接把论文训练小时当成最终账单。

### 7.3 环境必须分离

官方仓库也提示 LLaVA 与 CadQuery/IOU 依赖冲突，建议至少分成：

```text
cadcoder-vlm     # torch、LLaVA、transformers、deepspeed、flash-attn
cadcoder-cad     # cadquery、OCP、trimesh、plyfile、IOU与渲染
```

当前 CADmium 的 `.venv` 保持不变，避免把 `transformers==4.37.2`、`torch==2.1.2` 等论文代码依赖覆盖到已有1.5B复现环境。

## 8. 工程化必须额外解决的问题

### 8.1 模型代码执行安全

CAD-Coder 输出的是任意 Python。官方脚本会写入 `.py` 后直接调用 Python 子进程，未设置超时，也不是安全沙箱。正式工程不得在宿主机直接执行未经审查的模型输出。

最低安全边界：

- 每个案例使用一次性容器；
- 容器非 root 用户；
- `--network none`；
- 根文件系统只读，只挂载单案例输出目录；
- CPU、内存、进程数和运行时间限制；
- 只允许 `cadquery`、`math` 等白名单 import；
- 禁止 `os`、`subprocess`、`socket`、文件遍历和动态下载；
- 超时后终止整个进程组；
- stdout、stderr、退出码和超时原因全部保存。

### 8.2 状态机

建议统一记录：

```text
C0 pending
C1 model_loaded
C2 response_generated
C3 code_extracted
C4 syntax_valid
C5 cad_executed
C6 step_exported
C7 metric_computed
C8 figure_rendered
F1 model_load_error
F2 generation_error
F3 code_extract_error
F4 syntax_or_runtime_error
F5 no_solid
F6 cad_kernel_error
F7 step_export_error
F8 metric_error
F9 timeout_or_security_reject
```

### 8.3 结果可追踪

每条 `result.json` 至少保存：

- `case_id`、源数据 ID；
- 图片/STEP SHA256；
- 模型 ID 与 revision；
- 仓库 commit；
- prompt、conversation mode；
- temperature、max_new_tokens、seed；
- 原始回答、抽取代码；
- token数、耗时、峰值显存；
- VSR、STEP/STL状态；
- IOUbest 与统计口径；
- 圆角验证结果；
- 环境锁文件和执行器版本。

## 9. 指标和验收标准

### 9.1 图4类似实验

最低验收：

- 5/5案例数据配对完整；
- 10次推理均保存原始输出，不丢失败样本；
- 对每个案例分别给出 `IOUbest(real)`、`IOUbest(rendered)` 和差值；
- 分别报告 VSR、STEP生成率；
- 输出四行五列例图和机器可读 CSV/JSON；
- 对比例误差、多次拉伸遗漏、薄板厚度误差做案例解释；
- 明确样本量为5，不做“普遍泛化能力已证明”的结论。

建议同时报告两种均值：

```text
official_conditional_mean = 只对成功执行样本计算 IOUbest
failure_penalized_mean    = 失败样本按0计入，用于工程端到端成功质量
```

### 9.2 图5类似实验

单案例成功必须同时满足：

1. 第二轮脚本可执行；
2. 最终变量 `solid` 存在；
3. STEP/STL 成功导出；
4. 几何不等于未修改基础实体；
5. 圆角曲面/边特征经程序或人工复核确认；
6. 强提示与抽象提示分别记录；
7. 不因一次成功就宣称具备稳定的未见操作泛化能力。

### 9.3 与论文数值的比较规则

- 使用同一模型、同一100样本、同一 BF16/解码配置时，才对比论文的 VSR=100%、IOUbest=0.675；
- 量化模型、不同样本、自建真实照片只能报告“本次工程结果”；
- 若使用本项目原有 Chamfer Distance，必须作为补充指标，不能替代论文 IOUbest；
- `watertight=True` 只说明网格封闭，不能证明图片语义、比例或圆角正确。

## 10. 测试计划

### 10.1 单元测试

- code fence、纯代码、前后解释文本的提取；
- 空输出、截断输出、没有 `solid` 的处理；
- manifest 必填字段、SHA256、重复 ID；
- IOUbest 的平移/缩放/轴翻转不变性；
- 圆角半径过大导致 CadQuery 失败时的错误分类；
- 沙箱超时、禁用 import、网络禁用和写目录限制。

### 10.2 集成测试

- Ground Truth CadQuery → STEP → STL → 渲染；
- 同一 STEP 自比较 IOU≈1；
- 云端模型1条 → 本地安全执行 → 指标 → 图表；
- 中断后从 JSONL 断点继续，不重复覆盖成功案例；
- 5条双输入域批处理完整生成图4式拼图。

### 10.3 回归测试

固定1个简单样本、1个多拉伸样本、1个圆角样本。变更 tokenizer、CadQuery、OCP、量化配置或绘图代码后都重新运行，比较 VSR、IOU、STEP体积和图片 hash。

## 14. 风险清单

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| 图4原始照片未公开 | 不能逐像素复现原图 | 自建成对真实照片案例，明确标为 similar reproduction |
| 图5 Qwen变体权重未公开 | 无法直接复现三模型列 | 先发布版+Oracle+代码编辑基线；精确复现另立训练项目 |
| 13B BF16显存不足 | 模型加载失败/OOM | 48GB以上；24GB仅做4bit近似 |
| LLaVA依赖较旧 | 与当前环境冲突 | 独立环境/容器，固定版本 |
| CadQuery/OCP依赖冲突 | STEP/IOU失败 | VLM与几何环境分开 |
| 模型生成任意Python | 宿主机安全风险 | 无网络、非root、只读、限时限资源容器 |
| 输出截断 | 代码中途结束，VSR下降 | 4096上下文、3450输出上限、保存 token 统计 |
| 真实照片尺度不可知 | 绝对尺寸无法评价 | 按论文先归一化并对齐；另报比例误差 |
| 只挑成功样例 | 产生选择性汇报 | 先固定 manifest，再运行模型，不删失败案例 |

## 15. 复现边界声明

本方案中，使用官方发布13B模型和自建真实照片得到的结果，属于“论文对齐的类似案例复现”；使用24GB显卡上的4bit模型、文本代码编辑模型或小样本 LoRA 得到的结果，属于“资源优化工程实验”。只有使用同一测试集、同一模型变体、相同训练/推理配置和相同指标口径，才能称为论文数值复现。

在原始图4照片和图5两个 Qwen 变体权重缺失的情况下，不应宣称已经精确复现论文图4、图5。可以严谨地表述为：已经复现其任务设计、执行链路、评价方法及类似案例，并记录了与论文材料和资源条件的差异。
